# FinScholar - App Context & Roadmap

This document serves as the single source of truth for the app's current state, features, and future roadmap so that the development context is never lost.

## 📱 App Identity
- **App Name:** FinScholar
- **Package Name:** `com.lalex.finscholar`
- **Data & Privacy:** Uses Supabase for backend authentication, but login is completely OPTIONAL. Users can use the app 100% locally. If they choose to log in to sync data, the app collects their Email. Requests Camera permissions strictly for scanning syllabuses/schedules locally.

## ✨ Current Features (V1)
1. **Grade Tracker:** Calculate and track GWA/grades.
2. **Auto-import Schedule:** Uses the camera to scan and parse class schedules.
3. **Auto-import School Calendar:** Uses the camera to scan academic calendars.
4. **Track Tasks:** To-do list for assignments and exams.
5. **Flashcards:** Study tool for students.

## 🧭 First-Run Onboarding (Implemented)
- **Route order:** `app/index.tsx` decides where a launch lands. Fresh install with no session and no local ledger → `/onboarding`; anyone else keeps the old behaviour (`/(tabs)` when signed in, `/welcome` otherwise).
- **Intro flow (`app/onboarding.tsx`):** four swipeable slides — meet Fin, feature tour, notification opt-in, local-first/optional-sync. Skippable at any point, then `router.replace('/welcome')` so the sign-in choice is unchanged. It writes no ledger data, so signing in afterwards cannot create a sync conflict.
- **Flags (`services/OnboardingService.ts`, AsyncStorage, local only):**
  - `@onboarding_completed_v1` — intro finished or skipped.
  - `@getting_started_dismissed_v1` — dashboard checklist hidden.
  - `@notification_opt_in_v1` — `granted` / `denied` / `skipped`.
  - `isFirstRun()` is the guard used everywhere: false as soon as the flag is set **or** a `grade_ledger_v2_data` ledger exists, so updating users are never sent back through onboarding.
- **Notification permission is deferred:** `app/_layout.tsx` only calls `NotificationService.ensureAndroidChannel()` on a first run and asks for the OS permission inside the onboarding slide. Existing installs still call `initNotifications()` on launch exactly as before.
- **Quick term setup (`components/onboarding/TermSetupModal.tsx`):** bottom sheet that creates a school year + semester (with optional dates) and selects it, so a new user is not dropped into the raw Academic Terms manager. Reached from the dashboard empty state; "Manage Academic Terms" is still there as a secondary link.
- **Getting Started checklist (`components/onboarding/GettingStartedCard.tsx`):** dashboard card tracking term → subjects → schedule → first task. Auto-hides when complete, dismissible, restorable from Settings.
- **Pure logic lives in `utils/onboardingProgress.ts`** (`suggestSchoolYear`, `deriveOnboardingProgress`, `createTermInLedger`) and is covered by `__tests__/onboarding.test.js`.
- **Settings → Help:** "Take the Guided Tour", "Replay Intro Slides" (`/onboarding?replay=1`, returns via `router.back()`) and "Show Getting Started Checklist".

## 🔦 Guided Spotlight Tour (Implemented)
- **What it is:** a coach-mark overlay that dims and blurs the screen, cuts a lit hole around one real control, pulses a ring on it, and explains it in a card that points at it. It is the primary onboarding guidance; the Getting Started checklist is the passive companion to it.
- **Provider:** `components/spotlight/SpotlightProvider.tsx` sits at the root of `app/_layout.tsx`, wrapping the `Stack` so the overlay paints over screens *and* the custom tab bar. It keeps a registry of targets, drives step state, and measures.
- **Measurement:** targets wrap themselves in `SpotlightTarget` (`collapsable={false}`). The provider measures the target and the overlay container in window coordinates and subtracts, so the highlight lines up regardless of status-bar/edge-to-edge offsets. It retries for ~2.6s while a screen settles; if the control never appears the step still shows, centred and unanchored, so a tour never dead-ends.
- **Cut-out technique:** four **fixed screen-sized** opaque panels, each moved by `translateX`/`translateY` only, form the complement of the highlight rect — so the target stays crisp with no masking library. They overlap in the four quadrants, so they live inside a group that carries the alpha (`opacity` + `needsOffscreenAlphaCompositing`): the group composites once and *then* fades, which is what keeps the dim uniform despite the overlap.
- **Everything that moves runs on the native driver.** Only the hole's *position* is animated (`translateX`/`translateY`); its *size* is plain layout that changes once per step, never per frame. An earlier version animated each panel's `top`/`left`/`width`/`height`, which put a full layout pass on the JS thread every frame and made the transition stutter badly — do not reintroduce that. The scrim is a solid colour rather than a `BlurView` for the same reason: a blur that resizes re-rasterises its backdrop every frame.
- **Step transition (no flicker):** the card's content lags behind the step index. Pressing Next fades the old card out (130ms) while the spotlight glides (300ms, ease-out cubic); only then does the copy swap, and the card is re-seated *while invisible* using the freshly measured rect before fading back in (90ms delay + 200ms). The provider reports `highlightReady`, so the card is never revealed against the previous control's position. A late height correction after reveal glides over 160ms instead of jumping. Card opacity and translation run on the native driver.
- **Card position and card opacity are owned by two separate effects, deliberately.** The card measures itself via `onLayout`, which feeds `cardHeight` and therefore `layout.top`. Putting `layout.top` in the deps of the effect that animates `cardOpacity` makes its cleanup cancel the fade-in mid-delay and strand the card at opacity 0 — an invisible tour. Keep the opacity effect's deps limited to `[canReveal, shown.index]`.
- **Fail-safe:** if a measurement has not landed within 600ms the card reveals anyway and slides into place when the rect arrives, so the tour can never sit there invisible.
- **Geometry** lives in `utils/spotlightGeometry.ts` (`inflateRect`, `resolveTooltipLayout`, `highlightRadius`) — pure, and covered by `__tests__/spotlight.test.js`, including safe-area and small-screen cases.
- **Tours** are declared as data in `constants/tours.ts`:
  - `MAIN_TOUR` (7 steps) — term selector, each of the five non-home tabs, settings. Every target is on the dashboard or the tab bar, which mount together, so the tour never navigates mid-flight.
  - One-step first-visit nudges for Grades, Schedule, Calendar, Tasks and Study, pointing at each screen's primary action.
  - `SPOTLIGHT_IDS` is the single source of target ids; a test asserts every step points at a known id.
- **Triggering:** `useScreenTour(key, steps, ready)` runs a tour once per install, waiting for the screen's data before measuring. Tour completion is stored under `@tour_seen_v1_<key>`; `markExistingUserOnboarded()` presets all of them so upgrading users are never interrupted.
- **Controls:** tap anywhere to advance, Back/Next/Done in the card, "Skip tour", and Android hardware back dismisses the tour instead of navigating behind it.
- **Replay:** Settings → Help → "Take the Guided Tour" clears every tour key, returns to the dashboard and restarts; the Getting Started card also has a "Show me around" button.
- **Adding a target:** wrap the control in `SpotlightTarget` with an id from `SPOTLIGHT_IDS`, then reference that id from a step. Register an id from exactly one mounted place — `Tabs` takes an optional `spotlightId` prop precisely so only the dashboard's term selector registers.
- **Changelog:** `ChangelogModal` no longer fires on a fresh install — it records the current version silently so "What's New" starts from the next update.

## 🎨 Visual Language: Tactile Bento (Implemented)
- **No drop shadows.** Depth comes from a tonal step plus a **2px darker bottom border** on `Card` and on pressables — a "lip" that reads as a solid object resting on the page. Blurred shadows under every element were what made the old screens feel like floating AI-template cards. `Shadows` still exists in `constants/Theme.ts` for legacy screens; do not add it to new dashboard work.
- **Cool indigo-tinted canvas, matched to the entry screens.** Light is `#f4f5fb` with `#e3e5f0` borders — off-white so the page never reads as a blank document, but in the same cool family as the welcome/login hero (`#4f46e5`, `#1e293b`, `#e8e8f4`). Dark is `#12132b` with a `#1b1d3a` / `#262a4d` ladder, matching welcome's `#1a1f3d` card. **A warm off-white was tried and reverted**: it made entering the app from the indigo login screen feel like switching products. Keep new neutrals cool.
- **`theme.lip`** is the bottom-edge colour every raised surface and pressable uses. One token, not a hardcoded pair.
- **Text contrast was raised, not just recoloured.** Light `textTertiary` measured ~2.6:1 on the old page — it is now `#6b665f` (~4.8:1), and dark `textTertiary` lifted to `#7c8494`. These carry 10–11px labels, so they need it.
- **`Tints` / `getTints(isDark)`** in `constants/Theme.ts` is the colour code: violet = grades, emerald = attendance, amber = tasks, indigo = schedule, sky = tools, red = danger. Each has `fill` (panel wash), `line` (inner border), `ink` (legible foreground on `fill`) and `solid` (rails, active states). **Use a tint only where it carries meaning** — a domain, a risk level, an active state. Never to decorate.
- **Saturated colour is reserved.** Full-strength colour appears on active P/A/NC buttons, the NOW badge, overdue rows and risk captions. Everything else is a wash.
- **`Card` variants:** `raised` (default object surface), `sunken` (recessed shelf, e.g. the quick-action toolbelt), `flat` (outline only). `fill`/`border` accept a tint for a card that carries meaning.

  - `components/ui/SectionHeader.tsx` — plain type heading with optional `count` pill, `subtitle`, and a text action link. It is no longer a chip + big circular arrow.

Grouping the first four into one panel is what stops the page reading as a stack of unrelated widgets.

The current class is washed in the attendance tint and badged `NOW`; ended classes drop to 55% opacity. Room sits on its own line so it can never wrap under the clock icon.
- **`QuietState`** replaces the old `EmptyRow`: a low-contrast tinted strip, not a full card. An empty section should recede — two empty full-weight cards used to dominate the screen.
- **The subjects shelf is full-bleed** — the horizontal `ScrollView` breaks the page gutter and carries its own `paddingHorizontal`, so the first and last cards no longer clip at the screen edge. It snaps to card width. Each card has a colour cap and a **fixed-height name slot**, so cards stay the same height whether or not a subject has a name behind its code.
- **Term and timeline are one card.** `Tabs` gained a `renderTrigger(open, label)` prop so the dashboard supplies its own trigger while reusing the shared `TermSwitcherSheet` and the `SPOTLIGHT_IDS.homeTerm` anchor. The timeline lives inside that card so the dates always belong to the term named above them; with dates missing it becomes a link to Academic Manager, and a term with only one date still shows it.
- **The status board separates by shape, never by rules.** It used to be one card cut into bands by two full-bleed hairlines, with the three numbers underneath divided by column rules. Row rules plus column rules is a table, and that is exactly how it read. Everything below the greeting is now an **inset rounded tile floating on the panel's surface with a gap** — the term tile and the three stat tiles — and there is not a single divider in the panel. **Do not reintroduce a hairline here.**
- **Colour on the stat tiles is a small round icon chip**, not a fill and not a rail. The tiles themselves take `softFill` (a neutral recessed tone), so the accent palette is not spent three times above the fold — the constraint the old colour rails existed to satisfy, met a different way.
- **`softFill` and `rowDivider` are the two tokens that keep it soft.** `softFill` is the fill for a tile that sits *inside* a panel. `rowDivider` is an **inset** rule (12pt from both edges) for list rows, positioned absolutely so it can drop into a flex row without disturbing it — full-bleed rules between uniform rows turn Today, Tasks and Upcoming into ruled paper.
- **Corner radii were raised across the dashboard** (board and first-run card to `Radius['4xl']`, list panels to `3xl`, subject cards to `2xl`, toolbelt icons to full circles, the app-bar settings button to a circle) after the screen was called "too sharp, too blocky, like an Excel sheet". The toolbelt is a plain soft shelf now rather than a bordered `Card`, since its border was another hard edge.
- **Fin has a habitat, not an avatar chip.** The status board opens with an illustrated header: two wave paths (`react-native-svg`) drawn into the tinted zone, two small sparkles, and `assets/images/FinDashboard.png` at 170pt bottom-anchored and bleeding off the right edge. The copy column is capped at `maxWidth: '58%'` so it can never collide with the art. Greeting is `"{greeting}, {displayName}!"` — `displayName` is the signed-in account's first name, falling back to **Scholar** (which is also what every guest sees, since auth is optional). Tapping anywhere still rerolls the tip (`getRandomQuote`). `FinDashboard.png` was an unused asset built for this screen; the animated GIF stays on the first-run welcome card only.
- **Getting started is sized to what is left.** Header with per-step pips and an `n/m` count, the single next step as a filled primary CTA, and a footer with "All steps" (expands to every step, completed ones included, so nothing became unreachable) and "Show me around".
- **Startup** (`components/AnimatedSplash.tsx`): the splash takes a `ready` prop and only animates out once the app behind it is loaded, never before a 1.5s floor. It used to fade itself out on a fixed 2.5s timer while `app/_layout.tsx` kept it mounted until fonts finished — a slow load left an invisible splash over a blank screen. It exits by lifting and fading rather than zooming, and `app/welcome.tsx` springs its mascot from 0.94 (not 0.3) so the logo does not pop a second time on handover.
- **`useTabBarHeight()` from `components/CustomTabBar.tsx` is the one measurement of the floating bar**, and every screen with content at the bottom uses it. The bar is `position: 'absolute'`, so screens must reserve its height themselves; they used to hand-tune a number each, which drifts from the bar and silently clips the last row — Practice Test's options were unreachable behind it and Profile reserved 60pt for an 88pt bar. `academic-manager` reserved nothing at all. The hook and the bar's own `paddingBottom` share `tabBarBottomPadding()`, so they cannot drift apart. **Never hardcode a bottom inset for the tab bar.**
- **Bottom navigation** (`components/CustomTabBar.tsx`): a sliding pill painted behind the active icon; tab buttons are `minHeight: 52`. The bar is **opaque** (`theme.tabBg`) — at 95% alpha, page content ghosted through it as unreadable text behind the labels. All six destinations are unchanged.
- **Every dashboard action survived the redesign** — dev menu on logo long-press, paywall, sync indicator, settings, pull-to-refresh, term switcher, tour replay, scanner modal, term setup, P/A/NC attendance writes, task DONE writes, and all fourteen navigation targets.

## 🔍 Schedule Scanner — Two Engines (Implemented)
- **The scanner offers a choice, and the sheet opens for everyone.** `ScheduleScannerModal` presents two modes with a one-line explainer of the tradeoff:
  - **AI Scan** (PRO) — uploads to the `parse-schedule` edge function. Handles any layout, including grid timetables and angled photos. Needs internet, takes seconds.
  - **Quick Scan** (free) — `@react-native-ml-kit/text-recognition` runs entirely on-device. Instant, offline, nothing uploaded, no quota. Reads printed study loads well; weak on grid timetables.
- **The premium gate moved.** It used to block the whole sheet, which would have made the free on-device scanner unreachable. The sheet now opens for everyone; `isPremium` + `onRequestPremium` gate the AI *mode* inside it, and free accounts default to Quick Scan. **This is a monetization decision** — reverting means restoring the `SyncService.getIsPremium()` check on the Scan buttons in `schedule.tsx` / `index.tsx`.
- **Both engines emit the identical shape** (`{name, day, startTime, endTime, room, instructor}` with day/time as printed strings) and feed the same `handleScannedClasses`, so there is one import path and one conversion path — `utils/scheduleParsing.ts`.
- **A study-load row can hold SEVERAL meeting patterns.** The real format is `TH 08:00 AM - 10:00 AM, M 07:30 AM - 10:30 AM` in one Schedule cell, with `GLE202, NGE105` in one Room cell. `extractClassesFromRow` therefore returns an **array**: it finds every `DAY TIME - TIME` segment in the row and pairs each with the room at the same position. The first version assumed one day and the first two times per row, which silently dropped half the sessions of every two-pattern subject. The regression test is the user's actual table — 8 subjects → 13 segments → 14 timetable blocks.
- **The name is the course code plus its section**, not the row text. `CSIT227 G2`, `SOCSCI032 E3/D4`, `PE205 G4/G8` — the Description column is prose and was previously ending up inside block labels. The `C0` cluster column is explicitly excluded from being read as a section.
- **`ONLINE` is a valid room, not just a delivery mode**, so it is deliberately absent from the `NON_ROOM` filter; taking only the first token of each comma-separated part already drops the trailing `In-Person` / `Hybrid`.
- **`utils/ocrSchedule.ts` is the on-device reconstruction**, pure and tested (`__tests__/ocr-schedule.test.js`): flatten blocks to lines, group lines into rows by vertical band (tolerance scales with median line height), order each row left-to-right, then pull day/time/name/room out of the row text. It **requires a time** in the row and a day token that actually resolves, which is what rejects headers, totals and prose.
- **Day-token scoring matters**: multi-day codes and full words outrank a bare letter, so a section suffix like `G7` or a stray `M` cannot beat a real `Saturday` in the same row.
- **ML Kit is a native module** — adding or updating it requires a dev-client rebuild (`cd android && ./gradlew assembleDebug`, then `adb install -r -d`). The modal detects the "not linked" error and tells the user to use AI Scan meanwhile.

## 🔍 AI Schedule Scanner (Implemented)
- **It reads TWO document types**: a visual weekly timetable, and a study load / enrollment form (one row per subject, days as a code like `MWF`, time as a printed range). The prompt in `supabase/functions/parse-schedule/index.ts` names both and lets the model decide which it is looking at.
- **The model transcribes; the app converts.** The response schema asks for `day` and `startTime`/`endTime` as **verbatim strings** ("MWF", "8:00 AM"), never computed day indices or 24-hour floats. `utils/scheduleParsing.ts` does the expansion and arithmetic — deterministic, tested (`__tests__/schedule-parsing.test.js`), and free of model variance. Because nothing is left for the model to reason about, `thinkingBudget` is 0.
- **`normalizeScheduleDays` is the only day parser.** It handles numbers, arrays, full names, abbreviations (`Th`/`Thu`/`Thur`/`Thurs`/`R`/`H`), run-together codes (`MWF`, `TTh`, `MTWThF`), separated lists (`M,W,F` · `M/W/F` · `Tues & Thurs` · `mon tue wed thur`) and ranges (`M-F`, `Mon-Fri`, `Tue to Thu`). **Compressed parsing is all-or-nothing** — a token with any unrecognised letter yields `[]`, because skipping unknown characters mined day codes out of ordinary words ("TBA" → Tuesday, "nonsense" → Saturday) and invented classes from bad OCR reads.
- **It returns `[]`, not `[0]`, for unreadable input**, so a caller can tell "no days" from "defaulted to Monday" — that distinction is what stops phantom Monday classes.
- **Fixed: the two scan buttons disagreed.** `app/(tabs)/index.tsx` expanded `MWF` into three classes; `app/(tabs)/schedule.tsx` had its own single-day `normalizeDay` that silently collapsed every multi-day code to Monday. The same scan produced different timetables depending on which button started it. Both now import the shared util — **do not reintroduce a local day parser in a screen.**

- **Failures are classified, not displayed raw.** `components/schedule/ScheduleScannerModal.tsx` calls the `parse-schedule` Supabase edge function (deployed only — not in this repo), which relays the model provider's own error text. `utils/scannerErrors.ts` decides whether that text is transient (`isTransientFailure`) and what the student sees (`friendlyScanError`). A provider overload — "This model is currently experiencing high demand…" — becomes "Fin's scanner is busy right now", because "model" is not a word a student should be shown.
- **Bounded retry.** Transient failures retry up to `MAX_SCAN_ATTEMPTS` (3) with `SCAN_BACKOFF_MS` (1.2s, 3s), showing "Scanner is busy — retrying (n of 3)…" so it never looks frozen. Permanent failures (bad image, not logged in, low credit) break out immediately — never retry those, it just burns the user's time and the provider's capacity.
- **The word boundaries in that regex are load-bearing** and covered by `__tests__/scanner-errors.test.js`: without ``, a request id containing `429` would look like a rate limit and trigger pointless retries. An earlier inline version of this shipped a literal backspace byte where `` was intended, which silently disabled the whole status-code branch — hence the extraction to a tested util.
- **Images are downscaled before upload.** `expo-image-manipulator` shrinks the longest edge to 1568px at JPEG 0.7 when picking, falling back to the picker's own base64 if it fails. A 12MP photo is several MB once base64-encoded — slow to upload, and close to the edge function's request limit — and the provider downscales to ~1568px anyway. **This added a native module: a dev-client rebuild is required.**

## 🗓 Timetable Blocks & Scan Reveal (Implemented)
- **Blocks are painted SOLID**, from `ClassPalette` / `getClassColor(colorIdx, isDark)` in `constants/Theme.ts` — six indexed fills, each with an `edge` for the app's bottom lip, white text on top. They used to be a 20%-alpha wash with coloured text, which read as a smudge over the grid lines and fought the text at low zoom. The three local palettes in `TimetableGrid.tsx` (`COLORS`, `EXPORT_DARK_COLORS`, `EXPORT_LIGHT_COLORS`) are gone; the theme is the only source, so the grid, the dashboard's Today rows and the export all agree.
- **Selection** swaps the lip for a full ring (white in dark, near-black in light) and tints the check to the block's own colour.
- **Scan reveal:** `handleScannedClasses` bumps `revealToken`, which `TimetableGrid` passes to each `ClassBlock` as `appearToken`. Blocks then replay a 320ms fade + scale + rise, staggered 55ms apart in **chronological order** (`appearIndex`, computed in the same `useMemo` as the overlap layout), capped at 1.6s total. Export mode never animates — it must render instantly for `ViewShot` to capture it.
- **The post-scan hand-off is sequenced, and must stay that way.** `handleScannedClasses` closes the scanner, waits 280ms for that sheet to slide out, *then* bumps `revealToken`, and only holds the "check my work" prompt until `280 + revealMs + 400`. Firing all three on the same tick — which is how it first shipped — played the entire fill-in behind two modals, so it looked like nothing animated at all. Timers are tracked in a ref and cleared on unmount.
- **Adding an inline arrow or fresh object to a `ClassBlock` prop still kills the memo** (see Schedule Performance); `appearIndex`/`appearToken` are plain numbers for exactly that reason.
- **Scanner progress** (`ScheduleScannerModal.tsx`): the picked image is shown at 55% opacity under a sweeping indigo band with corner brackets, driven by a native-driver `Animated.loop` gated on `isProcessing`. It replaced a bare `ActivityIndicator`, which gave no sense that the student's own image was being read.

## ⚡ Schedule Performance (Do Not Regress)
- **The export tree is mounted only for the capture.** `app/(tabs)/schedule.tsx` renders the timetable at 3084px wide for image export — roughly a 2940×1920 offscreen view tree per theme, plus a 3084px `ImageBackground`. These used to be mounted whenever the tab was in grid view (the default), so every zoom, quick-edit toggle and attendance tap re-laid them out; that was the app's main source of lag. `exportRender` state now mounts them only while a capture/preview is in flight, **and only for the theme being captured**; `closeExportPreview()` drops them. Never move that back to an always-mounted condition.
- **`ClassBlock`'s `memo` depends on stable props.** The overlap layout in `TimetableGrid` is behind `useMemo([classes, displayDayIndices])`, `displayDayIndices` is memoised, `handleToggleSelect` is a `useCallback` that takes the id, and each block's room is resolved once into `displayRoom` so blocks no longer take the whole `classes` array. Before this, `processedClasses` rebuilt every class object on every render and the memo never once hit. Adding an inline arrow or a fresh array/object to a `ClassBlock` prop silently undoes all of it.
- `cls.room` stays the raw (possibly comma-separated) value because it reaches the details modal through `onPressClass`; `cls.displayRoom` is the resolved single room for the block.

## 🗓 Schedule Tab Layout (Implemented)
- **Principle:** the timetable is the content, everything else is chrome. `app/(tabs)/schedule.tsx` is a fixed-height column — app bar, view switch, actions + tools, digest, schedule — not a page that scrolls. The grid is on screen the moment the tab opens; nothing above it scrolls it out of view.
- **App bar:** identity + PRO badge, with the **term switcher as the subtitle chip** underneath. `components/ledger/Tabs.tsx` takes a `compact` prop for this; both variants open the same `TermSwitcherSheet`, so the term list has one implementation.
- **Action + tools row:** directly under the view switch — **Scan** and **Add** as compact pills on the left, then Quick Edit, the zoom stepper and Export as icon-only buttons on the right. One 34pt row carries every control the schedule has. The action pills wrap the `SPOTLIGHT_IDS.scheduleAddClass` tour anchor.
- **Digest bar:** one tappable line showing today's date, today's class count and the ongoing/next class. It replaces the old hero banner, the four-metric stat card, the "Today" strip and the "Next class" strip that used to sit above the grid.
- **Overview sheet:** everything the digest bar summarises lives here — Fin's hero card and quote, the four term metrics (today's classes, weekly blocks, attendance rate, active term), today's classes, upcoming milestones, subjects missing class times, and **Reset Schedule** as the last, destructive row. Opened from the digest bar; nothing was dropped in the move.
- **Zoom and Quick Edit appear in grid view only; Export in grid and Glass.** Attendance shows just the action pills.
- **The schedule runs to the bottom of the screen.** There is no bottom dock: whichever view is showing pads itself by the tab bar's height (the bar is absolutely positioned), which is why the screen uses `SafeAreaView edges={['top','left','right']}`. Page gutter is the `GUTTER` constant (12pt), narrower than the app's usual 16 so the timetable gets the width.
- **`TimetableGrid` takes `fillHeight`** to stretch to the space it is given instead of its default fixed 600pt box. Export mode is unaffected.
- **Empty state:** a term with no classes renders `EmptyScheduleCard` in place of an empty week, so a blank grid never reads as a bug.
- **Deep links:** `?viewMode=` accepts `grid`, `list` and `attendance`; `glass` is normalised to `list` since that is the label the switch shows for it.

## 🗓 Calendar Tab (Rebuilt)
- **Principle: a day is not just its milestones.** The tab only ever read `sem.milestones`, so tapping October 14 could not tell a student they had three classes and a lab report due — that lived on two other tabs. `utils/calendarModel.ts` now flattens the ledger into one dated stream: **events** from every term's `milestones`, **task deadlines** from `subject.requirements[].dueDate`, and **classes** derived per-date from `sem.classes` using the app's Monday-zero `day` index. Classes and tasks are read-only here and deep-link to Schedule and Tasks.
- **Two lenses, one stream.** **Month** is the grid with the selected day's timeline inline underneath it; **Agenda** is a date-sectioned list of everything upcoming (or past) with sticky headers. The day view used to be a 60%-height modal, so comparing two days took four taps.
- **The day is ONE chronological timeline, not three lists.** Untimed items sit in an all-day strip at the top; everything with a clock — classes, deadlines, exams — falls into a single time-ordered list below it. An earlier pass grouped the day into "Calendar", "Due" and "Classes" cards, which made a student interleave three sections in their head to work out what came next.
- **The month view is ONE scrolling page.** `app/(tabs)/calendar.tsx` keeps the app bar and control bar fixed and puts the month header, grid and day timeline in a single `ScrollView` padded by `useTabBarHeight()`. It was first built as a fixed column with the grid pinned above a separately-scrolling panel, and on a real phone that left the day's content stranded behind the floating tab bar with nowhere to scroll to. **Nothing inside that page may own a nested vertical scroll** — `DayPanel` is a plain `View` for exactly this reason.
- **Chrome was collapsed into two bands.** App bar (identity + term chip + sync/scan/settings), then one control bar carrying the view switch, search, filters *and* the term strip. Three stacked banded rows read as chrome, not as a calendar. The original screen was worse still: a header, a full-width term selector, an "Auto-Import Events" banner and a "Semester Duration" card — roughly 260pt before the calendar itself.
- **`utils/calendarModel.ts` is the only date authority**, covered by `__tests__/calendar.test.js`. Two live bugs went with it: event dates were compared through `new Date(str).toISOString()`, which reports the previous day for anyone west of UTC, and the grid measured cells from `Dimensions.get('window')` read once at module scope, so rotation and tablets desynced the grid from its own weekday header. `toDateKey` / `parseDateKey` / `toDateKeyLoose` are local-time only.
- **The grid is flat.** No cell backgrounds, no cell borders, no radius — just numbers on the page. Only two days are painted: today's number takes `theme.primary`, and the selected day gets a solid `PIP` circle. The first pass gave all 42 days a filled bordered box and washed every in-term day indigo; it read as blocky and muddy and the numbers competed with their own containers. **Do not reintroduce a per-cell surface.**
- **Monday-first, and trailing empty weeks are trimmed.** Monday because `class.day` is Monday-indexed everywhere else and a Sunday-first grid put the week's classes in the wrong column. `buildMonthMatrix` always builds six rows (the most a month can span) and `trimTrailingWeeks` drops any final row that is entirely next month — September 2026 goes from six rows to five, saving ~50pt. Fixed six rows only earned their keep while a panel below had to stay put; once the page scrolls they are waste.
- **Marks are dots.** Up to three, one per *distinct* event type (repeats collapse to one dot, a fourth type becomes `+n`), plus an amber dot when the day has task deadlines. An earlier version drew a hairline under every class-meeting day — every weekday had one, which is no information at all, and next to the dots it read as a rendering artifact. Classes appear in the day timeline instead.
- **The term is drawn by subtraction.** Days outside `startDate`–`endDate` drop to 38% opacity; nothing inside the term is tinted. Colouring 30 cells that all mean "normal" spends a colour to say nothing. `getTermProgress` turns the two dates into "Week 7 of 19 · 66 days left" in the term strip, and the dates themselves live in `TermSheet` behind it — previously a permanent card showing two raw dates and no arithmetic. Term dates also gate class derivation, so a July Monday no longer shows a full timetable.
- **Rows are a time gutter plus a tinted block** (`CalendarRows.tsx`): a fixed 52pt clock column, then a rounded washed card with a 3pt solid left edge in the item's own colour — the same anatomy as the app's timetable blocks. They were first drawn as hairline-divided rows inside one bordered card, which made a day look like a settings screen rather than a schedule. Classes take a neutral fill with a coloured edge; a list of six solid blocks is a paint chart.
- **`components/calendar/calendarTheme.ts` is the one event palette.** `calendar.tsx` and `VisualCalendar.tsx` each declared their own `MILESTONE_TYPES` with **different hexes**, so one event was cyan as a dot and teal as a chip eight points below it. `getEventTint(type, isDark)` returns the `fill`/`line`/`ink`/`solid` shape `Tints` uses. `VisualCalendar.tsx` was deleted.
- **Events can be edited where they are.** Each item carries its own `yearId`/`semId`, so editing an event from another semester writes to that semester. The old screen could only mutate the active term and silently switched the student's whole term selection first.
- **Scope is now explicit.** The grid used to show every term's events while the list below showed only the active one, with no signal. A `This term / All terms` filter chip states the choice; search and per-type chips sit beside it. A type filter never hides task deadlines — picking "Exams" must not silently hide what a student owes.
- **New affordances:** search, per-type filters, jump-to-Today, horizontal swipe between months (`PanResponder` — the repo has no `react-native-gesture-handler`), quick Today/Tomorrow/Next-week date chips in the event form, and Upcoming/Past in the agenda.
- **Every action survived** — add, edit, delete, multi-select bulk delete (now in the agenda header), AI import via `CalendarImportModal` with its `SPOTLIGHT_IDS.calendarImport` tour anchor, term start/end editing, term switching, sync indicator, settings, and the cross-term event list. The import banner was dropped; the sparkle button in the app bar and the empty state's copy are its entry points, matching how the grades tab reduced "add subject" from three permanent buttons to one.
- **Forms run on `KeyboardSheet`.** The add/edit form was a bare `Modal` at a fixed `h-[70%]` with Save pinned to the bottom and no keyboard handling, so on a short phone the keyboard covered both the note field and the button.

## 🎴 Study Tab Layout & Keyboard (Implemented)
- **`components/ui/KeyboardSheet.tsx` is the app's sheet for anything with a text field.** The study tab had **no keyboard handling at all** — six bottom-anchored `Modal` + `justify-end` forms — so on "New Card" (two multiline inputs stacked above Save) the keyboard covered the Back field and the button outright. Three things in it are load-bearing:
  - `KeyboardAvoidingView` with **`behavior="padding"` on both platforms**. Android `Modal` renders into its own dialog window, which `adjustResize` does not resize, so the `Platform.OS === 'ios' ? 'padding' : undefined` pattern used elsewhere in this repo does nothing there. `padding` measures frame-vs-keyboard, so where the window *does* resize it computes ~0 and stays correct either way.
  - The body **scrolls**, so a form taller than the space left above the keyboard is reachable instead of clipped.
  - **`keyboardShouldPersistTaps="handled"`** — without it the first tap on Save only dismisses the keyboard and the user has to tap twice.
  - The **primary action goes in `footer`**, pinned above the keyboard, so it can never be the thing that gets covered.
- **All six sheets were rebuilt on it** — create, deck form, card form, import, exam prep, move — plus the new deck-actions sheet.
- **The eleven-button alert is gone.** `showDeckActions` called `AlertService.alert` with eleven actions; `CustomAlert` stacks >2 buttons vertically in a `max-w-sm` card **with no scroll**, so Export / Reset Progress / Delete rendered below the bottom of the screen on a normal phone. It is now a grouped, scrollable sheet (study · organise · danger) with all eleven actions and a one-line explainer each.
- **`manage` was folded into `detail`, and the view mode was removed from `StudyViewMode`.** The two views were ~90% the same screen — both listed cards with edit/delete, both had their own study CTA, import and add-card — but **search and status filters existed only in `detail` while bulk select, bulk reverse and per-card due dates existed only in `manage`**, so which half of the features a student got depended on which button they happened to press. The merged deck screen has all of it. Do not reintroduce a second card list.
- **The tab was the app's only neutral-slate screen.** `#1a1a1b`, `bg-slate-950`, `bg-[#121212]` and `Shadows.*` are replaced by `constants/Theme.ts` tokens and `Card`/`ProgressBar`/`AnimatedPressable`, so dark mode is the same indigo-tinted canvas as every other tab rather than looking like a different product. `FlipCard` now takes the deck colour as its bottom **lip** instead of a coloured cast shadow.

The decks landing lost its "Study Options" row card — a third route to the same screen the header gear already opens — and the duplicate "Add Deck" header; search and the filter chips now sit directly above the deck list they filter.

## ✋ Quick Edit: Direct Manipulation (Implemented)
- **Blocks are dragged, not nudged.** Quick Edit used to be tap-to-select plus a bulk toolbar of ±5-minute and ±1-day buttons, so moving a class two and a half hours was **thirty taps**. Press and hold a block (180ms) to pick it up, then drag it to any day and time; drag the grab bar on its bottom edge to change how long it runs. Both snap to the same five-minute grid the nudge buttons use, so the two ways of editing agree.
- **The gesture is `PanResponder`, deliberately.** The project has no `react-native-gesture-handler`, and adding one would force a dev-client rebuild. `ClassBlock` owns two responders: the move one refuses the gesture until the block has been lifted (`onMoveShouldSetPanResponderCapture`), and the resize one only claims on a clear vertical drag from the handle — otherwise the grid's two nested ScrollViews would never scroll again.
- **`draggingId` freezes both ScrollViews** for the duration of a drag. Without it the grid scrolls under the block being moved and the gesture fights itself.
- **`utils/quickEdit.ts` holds the arithmetic** — `snapToGrid`, `resolveBlockMove`, `resolveBlockResize` — because a gesture cannot be exercised by the test runner but the clamping is what stops a block landing on hour 25 or going to a negative duration. Covered by `__tests__/quick-edit.test.js` (18 assertions, including zero-width grids and blocks longer than the day).
- **Feedback while dragging:** the block lifts (scale 1.04) and swaps its lip for a white ring, a dashed ghost marks where it came from, and a pill at the top of the grid reads out the target slot (`Wednesday · 10:00 AM – 1:00 PM`). Snapping is applied *during* the drag, not on release, so the block visibly clicks into each slot.
- **The drag moves the block by re-rendering it in the target slot, never by a transform offset.** The first version translated the block and zeroed the offset on release, which put the block back at its old base for the frame or two before the parent's state update returned — every drop visibly rubber-banded home and then jumped to its destination. `ClassBlock` now holds a `ghost` slot that overrides the props while the drag is in flight *and* while the commit settles, clearing itself only once `cls.day` / `startHour` / `duration` agree (with an 800ms bail-out if the edit never lands). Because the drag snaps, this re-renders on slot changes, not on every touch event. **Do not reintroduce a translate-and-reset drag.**
- **Edge auto-scroll.** Manual scrolling is off while a block is in the air — otherwise the grid slides out from under the finger — so dragging into the top or bottom 76pt of the viewport scrolls the grid instead, 14px per 16ms tick. Each tick re-runs the block's own resolver, and `dragScroll.delta()` feeds the scrolled distance back in as extra drag, so the block stays under the finger rather than riding the content away. The viewport origin is re-measured on every pick-up, since the chrome above the grid changes height.
- **The Quick Edit panel no longer covers the schedule.** It was a two-line card pinned over the last hours of the day. It is now a single 38pt line that can be dismissed, it is hidden entirely while a block is being dragged (it sits exactly where a downward drag ends up), and the grid's scrollable content grows by `QUICK_EDIT_PANEL_SPACE` while the mode is on so anything underneath can be scrolled clear.
- **One-step undo** covers the last drag, resize *or* bulk nudge — direct manipulation makes an accidental change much easier, so the change has to be reversible. It clears when Quick Edit closes.
- **`ClassBlock`'s memo still holds.** The three new props (`onDragStateChange`, `onDragPreview`, `onCommitDrag`) are `useCallback`s with empty deps that read `classes` and `onUpdateClass` through refs — an inline arrow there would undo the whole optimisation (see Schedule Performance).
- **Everything the toolbar did survives**: select, select all, ±day, ±time, ±length and bulk delete. It is restyled to theme tokens, and while nothing is selected it explains the two gestures instead of sitting empty.

## 🧩 Home Screen Widgets (Rebuilt)

- **Five widgets, one design system.** `FinScholarWidget` ("Up Next"), `FinScholarAgendaWidget` ("Today"), `FinScholarDeadlinesWidget`, `FinScholarFocusWidget` ("Next Class", a 4x1 strip) and `FinScholarStatsWidget` ("Semester Pulse"). Each is declared in the `react-native-android-widget` block of `app.json` **and** in `WIDGET_REGISTRY` (`widget/WidgetTaskHandler.tsx`); a test fails if the two drift. Adding a widget needs a native rebuild.
- **What replaced the old one.** The previous widget was a single indigo gradient card with a wavy SVG divider, avatar initials and a 28dp circular badge that clipped any countdown longer than "2h". Its padding was mixed per edge (12/10/2/8), its corner radius was a fixed 32 at every size, and its row count came from three hard-coded height thresholds. All of that is gone.
- **The new look.** One padded card per widget (`widgetUi.surfaceStyle`) with a barely-there vertical gradient, and **exactly one filled block** — the hero panel on Up Next, painted in that class's own colour. Everything else is quiet: a 3–4dp colour rail, a fixed time column, the name, and a right-hand column. At widget scale a stack of filled pills turns into a smudge; one solid panel against plain rows gives a figure/ground the eye resolves at a glance.
- **Class colour is shared with the app.** `widget/widgetTheme.ts` mirrors `ClassPalette` from `constants/Theme.ts` and resolves by `colorIdx` (falling back to a name hash for classes that predate it), so a class painted indigo on the timetable is indigo on the home screen. A test asserts the two tables stay identical.
- **Geometry is computed, never guessed.** `widget/widgetLayout.ts` turns the launcher's `widgetInfo` into a scale (`xs`/`sm`/`md`/`lg`) with a gutter, radius, gap and type scale; `fitCount` decides how many rows actually fit in the space left over, and `distributeRowHeight` shares out the surplus so a tall card does not end in a dead band. The suites sweep a size matrix and assert the composed height never exceeds the widget — a clipped row fails the tests, not the phone.
- **Degradation is deliberate.** Narrow cards drop the room column before they clip a class name; short cards drop the header, then the hero (Up Next falls back to the compact strip); Semester Pulse drops to one row of tiles rather than showing four unlabelled numbers; Today windows onto the first class that has not happened yet.
- **`allowFontScaling={false}` on every `TextWidget`.** The library maps a scaling font to SP, so a phone set to "largest text" pushed rows straight out of a fixed-height card. DP keeps the drawn layout the size the metrics promised.
- **Nunito is bundled for widgets** (`assets/fonts/Nunito_{400Regular,700Bold,800ExtraBold}.ttf`, listed in the plugin's `fonts` array). It is loaded as a custom typeface, and Android does **not** fall back glyph by glyph — so widget copy stays inside Latin-1 plus `· – — …`. A symbol like ✓ or ☀ would draw as a tofu box; empty states use a small rule instead of a glyph.
- **Light/dark is drawn, not detected.** Every widget renders twice as `{ light, dark }`; the library saves both bitmaps and Android picks by system theme. The old code read `Appearance.getColorScheme()` inside the headless task, which is unreliable there and never fires again once the app is shut.
- **Deep links use `OPEN_URI`, never `OPEN_APP`.** The native provider ignores `clickActionData` for `OPEN_APP` and just relaunches the app on its last screen — the old widget's attendance deep link never actually worked. Up Next → the timetable, Today → the attendance day view, Deadlines → Tasks, Semester Pulse → the dashboard.
- **One read of the ledger feeds all five.** `widget/widgetData.ts` is pure (`buildWidgetSnapshot(ledger, { yearId, semId, now })` → `WidgetSnapshot`) and holds the schedule maths, due-date urgency, attendance, term progress and grade formatting. That is what makes the widget layer testable without rendering, and it means five widgets cost one parse rather than five.
- **The in-app gallery** (Settings → Home Screen Widgets) is a paged `WidgetPreview` of all five, driven by `WIDGET_GALLERY` and `buildDemoSnapshot()`, so a student sees the real layouts before adding one.
- **Refresh cadence:** `updatePeriodMillis` is 1,800,000 (Android's floor); the app also refreshes on launch, on theme change, and after every `SyncService` data change. Countdowns can therefore go stale between ticks, which is why the hero leads with the **absolute** time and treats the countdown as a chip.

## 📣 Release Notes & Update Prompt (Rebuilt)

- **The changelog is data, not JSX.** `constants/changelog.ts` holds every release newest-first (`version`, `date`, `headline`, `items[]`), each item colour-coded by a `Tints` key so an entry is tinted by the area of the app it touches. It used to be a hardcoded list inside the modal, which is how 1.0.7 shipped still advertising flashcard features from 1.0.5.
- **A test stops it going stale.** `__tests__/release.test.js` asserts `LATEST_RELEASE.version === app.json version`, that `package.json` agrees with `app.json` (they had drifted 1.0.5 vs 1.0.7), that entries are unique and ordered newest-first, and that every item has a real description and a valid tint. **Bumping the version without writing release notes now fails `npm test`.**
- **"What's New" is theme-aware and reopenable.** The sheet was dark-only — `BlurView tint="dark"` over a glass background with white text — so in light mode it dropped a black slab over the app, and its stacked drop shadows were the floating-template look the rest of the app moved away from. It is now built on `getTheme`/`Tints`/`Radius`/`Typography` like every other surface, with a grab handle, a version + date line, and an **"Earlier updates"** section. `ChangelogService.open()` (same imperative shape as `AlertService`) drives it from **Settings → Help → What's New in vX.Y.Z**, so release notes are no longer a one-shot popup you can never get back to.
- **The action button is pinned, not scrolled.** The old sheet kept its only button at the bottom of the scroll view, so on a short screen you had to scroll a list you had already read just to dismiss it.
- **`UpdateWarningModal` was never mounted.** It was imported in `app/_layout.tsx` and never rendered, so nobody had ever seen it — which is why its `LAST_SEEN_VERSION_KEY` snooze was declared and never wired, and why its `CURRENT_CHANGELOG` array was dead. It is now mounted, themed to match, and rewritten:
  - **"Later" actually remembers.** The dismissed remote version is stored under `@update_snoozed_version`, so the prompt asks once per release instead of on every cold start.
  - **It names both versions** — "You have 1.1.0 → Latest 1.2.0". "A new version is available" on its own gives the user nothing to decide with.
  - **Mandatory updates are supported.** An optional `force_update` column on `app_versions` hides "Later", the backdrop and the grab handle, and re-titles the sheet "Update Required".
- **Version comparison lives in `utils/appVersion.ts`**, not in the component, so it is testable. It tolerates a leading `v`, a build suffix and a missing patch part, and treats anything whose first segment is not numeric as unparseable — otherwise a bad `app_versions` row reading `"latest"` would parse as `0.0.0` and prompt on every launch.
